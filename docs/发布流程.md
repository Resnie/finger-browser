# 桌面客户端发布流程

## 安全边界

- 普通执行 `npm run release` 只做本地检查，不构建、不发起网络请求、不上传，也不访问 GitHub。
- 只有显式传入 `--build` 才构建，只有显式传入 `--release` 才构建并上传。
- GitHub 令牌、代码签名证书和证书密码只能来自环境变量或 GitHub Secrets，禁止写入 `package.json`、`.env` 或脚本。
- 正式发布要求工作区干净、`package.json` 版本与当前提交标签完全一致。
- 正式发布会通过 HTTPS 查询已经部署的后端 `/health`，核对健康状态、正式三段版本号、真实 Git 提交号和所需接口能力；`dev`、`unknown`、预发布版本及本地验收后端均会被拒绝。门禁失败时不会构建或上传客户端。
- 当前 Git 历史曾包含过令牌和私钥；对外公开仓库前必须先轮换旧凭据，并另行批准历史清理。发布脚本不会擅自重写历史。

## 本地检查与构建

```bash
# 默认 dry-run
npm run release

# 只构建、不上传
node scripts/release.mjs --build --platform mac
node scripts/release.mjs --build --platform win
```

`--build` 仍会执行敏感信息扫描和前端构建。跨平台安装包应优先交给 GitHub Actions 在各自系统上生成。

## 正式发布

1. 先完成本地前后端联调和人工验收。
2. 使用中文提交信息提交所有修改并推送代码。当前本地 `origin` 指向本地代码托管地址；它不会自动进入 GitHub。正式发布前需要将同一提交安全推送或镜像到 `Resnie/finger-browser`，发布脚本自身不会执行 `git push`。
3. 将 `package.json` 的版本（例如 `0.2.0`）打成相同版本标签（例如 `v0.2.0`），再推送该标签。
4. 先发布后端并完成远端健康检查和敏感数据全量只读解密预检。当前客户端还依赖 `20261012_07_expand_browser_state`、`20261012_08_add_google_auth_revision` 的表结构与 `portable-profile-v1`、`google-totp-migration-v1` 接口能力；先审核执行扩展迁移，再切换后端，不能只更新客户端。
5. 在 GitHub 仓库变量中配置 `BACKEND_RELEASE_INFO_URL`，值为正式环境的 HTTPS `/health` 地址。
6. 在 GitHub Actions 手动运行“发布桌面客户端”。第一次选择 `dry-run`；确认成功后选择 `release` 并填写已推送的标签。
7. 当前工作流在 Windows 构建并上传；本次只发布 Windows。
8. 在 GitHub Release 页面验证安装包、`latest*.yml` 和校验元数据，再用已安装客户端验证自动更新，并按下述规则保留本地正式产物。

本地直接上传只用于应急，并要求当前提交已打标签：

```bash
RELEASE_TAG=v0.2.0 BACKEND_RELEASE_INFO_URL=https://api.example.com/health \
  ELECTRON_BUILDER_GH_TOKEN=<从安全环境注入> \
  node scripts/release.mjs --release --platform mac
```

不要把真实令牌写进命令历史；上例只说明变量名，实际应由密码管理器、CI 或临时受控环境注入。

## 发布展示规则

以后所有 GitHub Release 只保留版本号作为标题（例如 `0.2.3`），简介正文留空，不生成自动发布说明。Git 标签名称使用 `v<版本号>`，带注释的标签也只填写版本号（例如 `v0.2.3`）。变更说明、部署细节和验收记录保存在项目文档中。

`package.json` 的 `build.releaseInfo.releaseNotes` 固定为空字符串，防止构建时自动读取发布说明文件。正式发布脚本会检查标签注释，发现版本号以外的内容就停止发布。

GitHub 的“统一版本展示”工作流在发布、编辑 Release 后核验所有版本，并由正式发布工作流在上传完成后调用；也可以手动运行。它将标题统一为版本号、清空简介，并将带有额外内容的标签注释改为版本号，保留标签的原目标和全部发布附件。直接调用 API 发布也必须遵守本规则。

`chrome` 是内核资源的固定下载标识，不是应用版本，保留其标识和下载地址，简介同样为空。没有注释的历史轻量标签保留原状。

## 正式产物的本地归档

构建输出遵循 `package.json` 的 `release/${os}/${version}`，Windows 正式产物保存在 `release/win/<版本号>/`。GitHub Actions 在远端构建不会自动写入本机；发布后应从对应版本的 GitHub Release 下载一份，不能用候选包或重新构建的包代替已发布资产。

每个 Windows 版本目录保留 `fingerbrowser-Setup-<版本号>.exe`、对应的 `.exe.blockmap` 和该版本的 `latest.yml`。保存时核对三份文件的大小和 GitHub 资产 SHA-256，并核对安装包 SHA-512 与 `latest.yml` 一致；各版本的清单分别存放，保留历史版本。归档目录由 Git 忽略，不提交安装包。

## GitHub Secrets

发布令牌使用工作流自带的 `GITHUB_TOKEN`，权限仅在发布任务中提升为 `contents: write`。如需正式签名，可配置：

- `MAC_CSC_LINK`、`MAC_CSC_KEY_PASSWORD`
- `WIN_CSC_LINK`、`WIN_CSC_KEY_PASSWORD`

未配置签名 Secrets 时可生成测试安装包，但不应直接作为面向用户的正式版本。

客户端要求的后端能力集中维护在 `config/release-compatibility.json`。新增依赖接口时必须先提高后端能力清单，先部署后端，再更新该文件和客户端；不得通过跳过门禁的方式抢先发布客户端。

## 本地验收包不是正式发布包

`npm run build:local -- http://127.0.0.1:8889/api/v1` 将接口固定为隔离的本地后端。生成的验收包不能上传 GitHub Release，也不能作为自动更新产物；正式发布必须从干净、已提交的源码重新构建正式 HTTPS API 配置。验收包没有 Developer ID 签名，不代表签名、公证或 Windows 安装验收已完成。

应用图标源文件为 `public/app-icon.svg`；修改品牌图标后可用 `node scripts/generate-icons.mjs '<本机 Chromium 可执行路径>'` 生成 `public/app-icon.png`、`build/icon.icns` 和 `build/icon.ico`。提交这些生成资产，CI 打包不依赖本机内核进行图标生成。
